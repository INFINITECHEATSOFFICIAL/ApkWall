# Runtime code/library integrity checks

**Finding:** Runtime code integrity checking is a real defense when it compares selected loaded code or memory against trusted expected values established during the app’s build. It is not equivalent to checking an APK file’s signature or hashing a few ZIP entries. OWASP describes memory checksums as values recorded at build time and compared with corresponding loaded memory at runtime; it also warns that checksum code can itself be hooked or patched, and that relocations or runtime-patched instructions need normalization/exclusion to avoid false positives. [1]

**Build-time versus post-build:** A post-build transformer can, in principle, calculate hashes for chosen immutable DEX/native-library entries and inject startup code plus those expected hashes into the existing wrapper. This is a narrower, best-effort *on-device APK-payload check*, not general verification of executed code or runtime memory. A true memory/code check needs a defined set of protected regions, build-known expected values, runtime mapping to those regions, and handling for loader/runtime changes. OWASP’s description specifically frames the baseline as build-time information. [1] Android separately recommends integrity checks before loading code, and signing code to protect both code and its expected hash. [2]

**Post-build costs and limits:** Any transformed APK has to be signed again. Android requires signed APKs, and its v2+ scheme invalidates the signature after any change outside the signing block. [3] The resulting signer must be acceptable to the installation/update channel: Android’s release guidance identifies the app-signing key as the key used on users’ devices and ties update continuity to that key. A generic offline tool cannot reproduce the original publisher’s signature without their private key. [4] A digest and verifier embedded in the same transformed app are not an independent trust anchor: a capable attacker can patch the expected value or bypass the check. OWASP characterizes runtime integrity as an evolving cat-and-mouse defense, not a standalone solution. [1]

**Requirements for even a restricted implementation:** Specify and support exact protected payloads (for example, selected base-APK DEX and native libraries); inject checks into the existing factory/wrapper without breaking its delegation and initialization order; compute baselines after all transformations and before final signing; exclude or normalize mutable/runtime-relocated regions; test on the declared Android/ABI range and with each target app; and clearly disclose that the app must be resigned with a key compatible with the intended distribution/update path. A claim about loaded-code integrity additionally requires reliable runtime-to-file/memory mapping and coverage of dynamically loaded code, which cannot be inferred merely from an APK’s entries. [1] [2]

**Compatibility and false positives:** An arbitrary APK may use multidex, native libraries for several ABIs, custom class loaders, packed/encrypted code, or code loaded dynamically; a single/base APK may not contain all delivered code. Checking only packaged bytes misses injected or patched code in memory. Checking memory naïvely can reject legitimate ART/JIT/relocation effects; OWASP explicitly warns that runtime-patched instructions and pointers must be normalized or excluded. [1] Replacing or wrapping an `AppComponentFactory` can also interfere with app-specific component construction/initialization, so broad compatibility requires app-by-app tests. These risks make silent fail-closed behavior particularly dangerous for arbitrary apps.

**Recommendation:** Do **not** expose “runtime code/library integrity” as a generic, reliable protection toggle for arbitrary prebuilt APKs. If implemented at all, offer only a clearly named and documented limited payload-hash check for a constrained, tested APK subset, with explicit re-signing/update caveats and a safe failure policy. Do not label APK signature verification or file hashing as runtime memory/code integrity, and do not present an unimplemented or decorative toggle as active.

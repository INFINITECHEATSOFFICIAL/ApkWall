# Resource shrinking and resource-name obfuscation

**Finding.** Treat these as two different operations. Generic dead-resource shrinking is a build-time analysis, not a safe generic transformation of an arbitrary finished APK. Android’s current guidance configures it in the app’s release build and ties resource reachability to code analysis: optimized shrinking makes code and resources one reference graph, so items unreachable from the app can be removed. This depends on build inputs and app-specific keep rules that an APK-only utility does not have. [1]

Resource-name obfuscation is different: Google’s AAPT2 `optimize` command accepts an APK as input and emits an optimized APK. Its `--collapse-resource-names` option collapses names in the resource-table key string pool. Thus an offline, post-build **name-collapse-only** operation is technically real and does not require source code. It is not equivalent to removing unused resources and offers limited concealment: it changes metadata names, not the resource contents. [2]

**Safe product decision.** Do not expose a generic “shrink unused resources” option for arbitrary prebuilt APKs. Without source/build metadata, the utility cannot reproduce R8/AGP’s app-level reachability analysis or apply the app’s keep rules. AAPT2 does offer configuration-based pruning, such as removing resource variants for explicitly selected target densities, but that is target-specific selection—not proof that a resource is unused across the app. [2] A separately labeled “collapse resource names” option can invoke AAPT2 against a supported single APK, with strict validation and a clear compatibility warning; do not present it as generic shrinking or a security guarantee.

**Requirements and limits.** Name collapse requires a compatible AAPT2 `optimize` binary, a processable APK with a resource table, and a separate output APK. The Android documentation describes the command and the `--collapse-resource-names` flag; resource entries that must retain names can be exempted with `no_collapse` directives in a resource configuration file. An arbitrary APK-only wrapper usually lacks that app-specific configuration, so it cannot know which names need exemptions. [2] The post-processed APK must then be signed and verified. Any further APK modification after signing invalidates its signature; signing requires a private key and certificate. A utility without the developer’s original signing key cannot preserve the original signing identity, which can prevent upgrade-over-install and affect signature-based integrations. [3]

**Compatibility risks.** Android’s `Resources.getIdentifier()` resolves a resource by its name and returns `0` if no name is found. Apps or libraries that construct resource names dynamically, or look them up by name in Java/Kotlin, native code, reflection, configuration, or framework glue, can therefore break if names collapse. Static references by compiled resource ID are a different case, but an APK-only tool cannot reliably prove that all lookups are static. [4] For shrinking, the analogous false-positive risk is deleting resources reached only through dynamic lookup, reflection, native code, downloaded/configuration-driven names, or other non-obvious references. The upstream build-time pipeline can use app-specific keep rules; a generic post-build pass has no equivalent reliable evidence. Preserve all resource variants unless the device/configuration target is explicit and tested. [1] [2]

**Recommendation.** Reject a generic source-less resource-shrinking toggle. If offering a real selectable option, implement and label only the narrower AAPT2 resource-name-collapse transformation, and gate it on successful APK parsing, output integrity checks, test/install validation, and a user-provided signing key (or an explicit warning that the result will be re-signed and will not retain the original identity). Make clear it may break name-based lookups and is obfuscation of resource-table names, not removal of resources or robust protection.

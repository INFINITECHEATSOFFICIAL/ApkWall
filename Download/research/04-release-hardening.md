# Release-build hardening (debug flags, logs, test endpoints)

**Finding.** This is primarily a source/build-time release-engineering practice, not a single generic APK-protection operation. Android’s own release checklist says to disable debugging, deactivate/remove logging before building, remove test files, and replace test URLs/paths with production URLs. Build variants/source sets are the mechanism for including different settings and code in different builds. For an arbitrary prebuilt APK with no source/project, an offline tool cannot safely guarantee that all three classes of issue are fixed. A narrowly scoped manifest edit may be possible; blanket “release hardening” is not safe as a universal toggle.

**What can and cannot be changed post-build.**

- **`android:debuggable`:** The manifest flag is application-wide, controls whether the app can be debugged, and defaults to false. A tool can in principle inspect and rewrite a compiled manifest to set it false, but must correctly handle binary XML and preserve the package; this does not make DEX-level debug switches or WebView debugging settings equivalent to the manifest flag. Any APK modification invalidates its existing v2+ signature. Re-signing with the utility operator’s key changes the signer identity; without the original signing key the utility cannot preserve the publisher’s signature/update lineage. Thus a controlled manifest-only transformation may be offered only with explicit signing/identity caveats and validation, not represented as universal safe hardening.
- **Logs:** Android recommends sanitizing production logs and using R8 rules to remove selected log calls as part of the optimized build; its release checklist likewise says to remove logging before building. These are project/build transformations, not a guaranteed generic APK pass. Post-build DEX rewriting is theoretically possible but requires call-site and semantic analysis; it cannot reliably cover native code, custom logging frameworks, indirect logging, or distinguish sensitive from harmless messages. Blind removal can alter side effects/control flow or break app behavior.
- **Test endpoints:** Android’s release checklist explicitly tells developers to use production rather than test URLs/paths. Identifying the intended production endpoint is application/product knowledge, normally expressed in source/build configuration. A post-build string replacement cannot reliably find dynamically composed, obfuscated, encrypted, native, remotely configured, or library-owned endpoints, nor prove that a candidate endpoint is correct or API-compatible. Replacing an endpoint blindly can break functionality or redirect traffic to an unsafe/wrong service.

**Recommendation.** Do not provide an active generic “release hardening” toggle for arbitrary prebuilt APKs that claims to remove logs or test endpoints. Keep these as source/build-time release checks for apps whose project/configuration is available. If useful, offer a separate, explicitly limited **audit/report** (inspect manifest debuggable state and flag suspicious logging/test-host indicators without claiming completeness). A manifest-only debuggable=false transformation could be a separate opt-in advanced operation only if the tool transparently explains re-signing, original-key loss, and compatibility limits and validates the output; it is not equivalent to the full method.

## Sources

1. **Prepare your app for release — Android Studio.** <https://developer.android.com/studio/publish/preparing> — Release guidance says to turn off debugging, deactivate logging/remove `Log` and tracing calls before building, remove static test files, and update server/service URLs from test to production; it describes producing a signed, optimized release APK.
2. **Configure build variants — Android Studio.** <https://developer.android.com/build/build-variants> — Build variants combine build-type/flavor settings, code, and resources; source sets control which files are compiled and packaged, including debug-specific logging and permissions. This supports the source/project nature of reliably separating debug and release behavior.
3. **`android:debuggable` — Android Developers, Security.** <https://developer.android.com/privacy-and-security/risks/android-debuggable> — The flag applies to the application as a whole, defaults false, and enabling it makes app internals/resources easier to access through debugging; Android says to set it false when shipping.
4. **Log Info Disclosure — Android Developers, Security.** <https://developer.android.com/privacy-and-security/risks/log-info-disclosure> — Recommends sanitizing production logs and using R8 to remove selected/all log levels; says manual removal is prone to error and presents R8 as part of code optimization/build.
5. **App signing — Android Open Source Project.** <https://source.android.com/docs/security/features/apksigning> — Every installed APK must be signed; v2+ verification covers the APK and any modification outside the signing block invalidates the signature. A modified APK therefore must be re-signed, with signer-identity consequences.
6. **Debug pre-built APKs — Android Studio.** <https://developer.android.com/studio/debug/apk-debugger> — Android Studio can inspect prebuilt APKs and disassemble DEX to SMALI, but describes that view as not a fully decompiled set; source attachment is needed for source-level Java/Kotlin debugging. This illustrates that access to an APK is not equivalent to having its build project/source.

# Reflection and dynamic-loading protection for arbitrary APKs

**Finding.** Reflection and dynamic code loading are distinct techniques. Reflection resolves or invokes code at runtime; it does not hide or move that code by itself. Dynamic loading places some DEX outside the ordinary static DEX view and loads it at runtime. Both can raise reverse-engineering effort, but neither makes code secret once it is executed on a user-controlled device. OWASP describes both techniques separately and characterizes identifier renaming as part of the release-build process. [1]

**Decision: do not offer this as a generic, safe-on-any-APK toggle.** Source/build-time obfuscation (such as R8 identifier renaming, which uses program analysis and configurable keep rules) requires a build project and its configuration; Android documents it as a release-build optimization. [2] A post-build tool can attempt a DEX-aware transformation—rewriting callsites/identifiers for reflection or moving/encrypting DEX and adding a loader—but that is a different, app-specific binary rewrite, not a safe general toggle. Reflection-based invocation alone is not a security boundary; dynamically loaded logic can be recovered at runtime. [1]

**What the existing AppComponentFactory wrapper enables—and does not.** Android documents `instantiateClassLoader` as a pre-component hook to return a custom class loader and load app classes from sources other than the base/split APKs. This makes a wrapper a possible bootstrap point, not an automatic packer or compatibility layer. [3] A post-build implementation would still need to transform the target DEX, embed or package the payload, install the loader before any dependent class is resolved, preserve the original factory's behavior, and correctly route all manifest-declared application components. It cannot safely infer every app's loading and initialization assumptions from the factory hook alone.

**Minimum requirements for a conditional implementation.** At minimum: a complete DEX/manifest/resource-aware repackager; accurate treatment of all DEX files and app entry points; a bootstrap compatible with the app's existing `AppComponentFactory` and device API range; preservation of names and APIs required by reflection, framework callbacks and native code; tests on representative devices and app flows; and a valid signing key for the transformed APK. Android requires APKs to be signed to install, and updates require the same signing certificate as the installed app; a utility without the original key cannot preserve that identity or deliver an in-place update. [4] If the loader writes DEX/JAR/APK files at runtime, apps targeting API 34+ must mark each dynamically loaded file read-only before writing, or the system throws an exception; Android recommends avoiding DCL where possible. [5] This offline design can keep payloads local, but has no server-side trust anchor; embedded decryption keys and code can be inspected or captured at runtime.

**Compatibility and false-positive risks.** Class names or methods may be looked up by strings or framework conventions rather than static references. Renaming or relocating them can break manifest components, custom factories, providers initialized early, reflection, JNI, XML callbacks, serialization, dependency injection, or library/plugin class loading. Moving classes also risks duplicate-class, resource, native-library and class-identity/loader problems. Apps that expect a custom `Application`/factory or code to be available before the wrapper runs are especially fragile. Generic analysis cannot reliably distinguish intentional reflective use from removable or renamable code; false positives can cause startup crashes or latent feature failures. Apps distributed as a base APK but requiring splits/features are outside the stated single-APK guarantee.

**Recommendation.** Keep this unavailable as a general selectable protection for arbitrary prebuilt APKs. If product requirements justify it, label it experimental and enable only after a strict compatibility/eligibility gate and full install, startup, component, reflection/JNI, and regression testing. Prefer build-time R8/keep-rule configuration when source/build access exists. Do not represent the AppComponentFactory wrapper alone as active reflection/dynamic-loading protection.

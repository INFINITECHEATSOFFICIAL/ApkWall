# Root, debugger, and emulator detection in an APK-only protector

**Finding.** These are client-side runtime risk signals, not a build-time security guarantee. Because the tool already injects an `AppComponentFactory`-based DEX wrapper, a genuine *best-effort detection* option is technically possible without application source: the wrapper can execute runtime checks and record/act on their results, provided it is actually invoked in the target app's process and the APK can be safely transformed, re-signed, and installed. It is **not safe to promise universal, reliable detection or universal blocking on arbitrary APKs**. Ship only as explicitly best-effort and opt-in; do not imply that merely changing `android:debuggable` detects a debugger.

## What the checks can establish

- **Debugger:** Android's `Debug.isDebuggerConnected()` reports whether a debugger is currently attached. It is a runtime observation, not a guarantee that a debugger cannot attach later; periodic or strategically repeated checks require executing app code. The manifest's `android:debuggable` is a separate app-wide build/packaging setting (false by default), and Android recommends shipping it as false.
- **Root:** Root/artifact checks are runtime heuristics—e.g. files, properties, processes, or other indicators—not proof that a device is rooted or trustworthy. OWASP calls root detection a bypassable environment risk signal and cautions that custom ROMs, enterprise test devices, and security research devices can be flagged. OWASP recommends layering and proportional response; its preferred defense-in-depth guidance includes backend enforcement, which this offline product explicitly cannot provide.
- **Emulator:** Runtime heuristics can inspect build characteristics, emulator files, package indicators, and related signals. These are imperfect: artifacts vary and can be hidden/spoofed; Android 11+ package-visibility restrictions cause package-based false negatives unless package queries are declared (or broad visibility is requested, which has policy implications). OWASP describes emulator detection as an evolving cat-and-mouse problem, not a standalone solution.

## APK-only implementation boundary

No source/build integration is strictly necessary for **injected code that really runs**: post-build DEX/manifest transformation can add checks to the existing wrapper. The factory is a platform hook for component instantiation (application, activity, provider, receiver, and service) and can execute checks around those paths. However, this does not insert checks into every original app method or sensitive operation, nor does it provide the original developer's intended response policy. Android documents that the factory's instantiation hooks do not provide an already initialized `Context` or earlier access to component objects; app `Application.onCreate()` is a distinct startup hook and runs before activities/services/receivers but after content providers. Thus a generic transformation cannot claim complete coverage or seamless early interception just from the existence of the factory.

For a real selectable option, require at minimum: (1) compatible and parseable single/base APK with a usable DEX and manifest; (2) successful insertion/dispatch of the checker in the wrapper code paths actually used by the target, without clobbering an existing factory or application declaration; (3) Android-runtime/API-safe checks, no undeclared sensitive permissions or broad package visibility, and graceful behavior when a signal is unavailable; (4) valid APK rebuild/signing and installability; and (5) testing on supported Android versions, representative physical devices/emulators, and target-app startup/component paths. Existing factory/classloader constraints, multidex/DEX method limits, native or dynamically loaded code, split-dependent apps, signatures, and package visibility need explicit handling or exclusion. A report-only outcome is safer than terminating or disabling the app based on heuristics.

## Limits and risks

Checks run only where injected code executes and can be bypassed by patching the APK or modifying runtime behavior; OWASP explicitly notes that determined attackers can defeat anti-debugging this way. Emulator/root markers are not stable identifiers. False positives can deny legitimate custom-ROM, enterprise, test, or security-research users; false negatives arise from hidden artifacts, new emulators, modified system properties, and unobserved paths. Aggressive blocking can break app flows. Repacking necessarily changes the signed artifact: the output must be re-signed, so it is no longer the original publisher-signed APK and may fail signature-dependent update/integrity checks. Any manifest/package edits can also interact with target-SDK and platform behavior.

## Recommendation

Offer only as a **best-effort runtime detection** option with transparent scope and testable behavior, preferably reporting risk without automatic lockout. Do not label it “root-proof,” “anti-emulator,” or guaranteed debugger prevention. If the product cannot verify that the injected checker is reached on the target's actual component paths and preserve startup behavior, disable/refuse this option for that APK rather than showing a decorative active toggle. Build-time `debuggable=false` can be a separate hardening setting, not a substitute for runtime detection. Strong enforcement would require app-owner source/build integration and/or a trusted backend (excluded here).

## Sources

1. **Android Developers — `Debug` API reference** — https://developer.android.com/reference/android/os/Debug — `Debug.isDebuggerConnected()` determines whether a debugger is currently attached; `waitingForDebugger()` only reports threads waiting for one.
2. **Android Developers — `android:debuggable` security risk** — https://developer.android.com/privacy-and-security/risks/android-debuggable — The manifest flag is app-wide, defaults false, and when true enables debugging; ship it false. This is distinct from active runtime detection.
3. **OWASP MASTG-BEST-0030 — Implementing Root Detection** — https://mas.owasp.org/MASTG/best-practices/MASTG-BEST-0030/ — Root detection is a bypassable environment-risk signal; custom ROMs, enterprise test devices, and research environments can be flagged; use proportional layered defenses.
4. **OWASP MASTG-KNOW-0031 — Emulator Detection** — https://mas.owasp.org/MASTG-KNOW-0031/ — Lists runtime build/file/package indicators and caveats, including Android 11+ package visibility causing package-check false negatives; detection is cat-and-mouse and bypassable.
5. **Android Developers — `AppComponentFactory` API reference** — https://developer.android.com/reference/android/app/AppComponentFactory — Describes factory methods as instantiation hooks for app components and states they do not provide earlier access to initialized component objects/context.
6. **Android Developers — `Application` API reference** — https://developer.android.com/reference/android/app/Application — An `Application` subclass is declared in the manifest; `onCreate()` runs before activities, services, and receivers (excluding content providers), and should be quick. This is a separate lifecycle location from component instantiation.
7. **OWASP MASTG-KNOW-0028 — Anti-Debugging** — https://mas.owasp.org/MASTG-KNOW-0028/ — Describes `isDebuggerConnected()` as a detectable JDWP signal, distinguishes native ptrace debugging, and documents bypass/coverage limitations.
8. **OWASP — Android Anti-Reversing Defenses** — https://mas.owasp.org/MASTG/0x05j-Testing-Resiliency-Against-Reverse-Engineering/ — Client-side anti-reversing measures do not assure effectiveness; a determined attacker can patch the binary or modify runtime behavior.

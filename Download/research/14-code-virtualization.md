# Code virtualization and protection SDKs

**Finding:** Code virtualization converts selected compiled method bodies into a custom instruction set interpreted by a generated VM; it is an obfuscation/hardening transformation, not a general runtime switch. Guardsquare describes DexGuard virtualization as analysis and rewriting of methods **at build time**, with generated VMs/instructions packaged in DEX. The original source is not conceptually required if a capable transformer can correctly analyze and rewrite compiled DEX. However, the cited commercial implementation is a compiler/build-pipeline product integrated with Android Studio/Gradle, not evidence of a safe, generic arbitrary-APK postprocessor.

**Answer for this product:** Do **not** expose an enabled “code virtualization SDK” option for arbitrary prebuilt APKs merely because an AppComponentFactory DEX wrapper exists. That wrapper may control app startup/class loading, but it does not virtualize existing compiled methods. A real post-build option is technically conceivable only with a vendor/tool explicitly supporting this input and transformation mode; otherwise mark unavailable/unsupported rather than adding a decorative toggle. Do not imply that an SDK requiring project/build integration can protect arbitrary APKs offline.

**Requirements and limits:** A genuine implementation needs a DEX-aware transformation engine that can parse and rewrite every relevant DEX, select supported methods, insert/link the VM runtime and configuration, preserve method contracts and Android packaging metadata, then produce a valid APK. In practice, require vendor documentation/support for arbitrary post-build base APKs, a compatible and preferably unpacked/single base APK, access to any needed protection SDK/runtime and configuration, and a complete install/launch/regression test process. Re-signing is mandatory after changes; require an authorized signing key/certificate. Without the original app-signing key, the modified APK cannot retain the original signer identity, so it cannot normally update the installed original or satisfy signer-based trust relationships. An offline utility must not silently sign with its own key and present the result as the publisher's app.

Virtualization does not stop runtime inspection or guarantee tamper resistance. It makes static analysis harder. It is best applied selectively to sensitive, supported methods: Guardsquare warns that loops, recursion, and numeric-heavy methods can slow substantially because the virtualized instructions are interpreted rather than optimized by AOT/JIT. Every protected build needs broad device/OS testing. False-positive/compatibility risks include unsupported DEX patterns, reflection/JNI or framework interactions that depend on names/metadata, broken startup/manifest wiring, altered signing identity, and security products or store review treating unusual packing/obfuscation as suspicious; the latter is a plausible operational risk, not a documented claim that virtualization alone causes detection. If implementation adds encrypted/dynamically loaded code rather than in-place DEX virtualization, Android's dynamic-code-loading guidance adds integrity and policy risks; remote loading is expressly outside this user's scope.

## Sources

1. **“DexGuard introduces code virtualization for Android apps”** — [Guardsquare](https://www.guardsquare.com/blog/dexguard-introduces-code-virtualization-android). Supports: method bodies become instructions for a randomized VM; transformation happens at build time; the virtualized result is packaged in standard DEX and interpreted at runtime; performance costs can be substantial for loops, recursion, or numeric operations; method targeting can manage overhead.
2. **“DexGuard”** — [Guardsquare product documentation](https://www.guardsquare.com/dexguard). Supports: current product describes code virtualization and compilation-time injected protections; compatibility/integration with Android Studio and Gradle, transparent integration into the app build; a compiler-based workflow rather than a generic arbitrary-APK utility.
3. **“apksigner”** — [Android Developers](https://developer.android.com/tools/apksigner). Supports: modifying an APK after signing invalidates its signature; signing requires the signer's private key and certificate, and `apksigner` verifies signatures.
4. **“Dynamic Code Loading”** — [Android Developers, Security](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading). Supports: dynamic code loading creates tampering risk; Android recommends avoiding it absent need and using trusted storage/integrity checks; many forms, especially remote sources, violate Google Play policy. Applies if a proposed design loads separate code, not automatically to in-place DEX virtualization.
5. **“MASTG-KNOW-0033: Obfuscation”** — [OWASP Mobile Application Security](https://mas.owasp.org/MASTG-KNOW-0033/). Supports: Android Java/Kotlin executes as DEX; obfuscation changes names, literals, control flow, or loading behavior to make decompilation/recovery harder; packing/dynamic code loading is a distinct way to hide logic until runtime.
